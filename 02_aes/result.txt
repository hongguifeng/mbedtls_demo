════════ 实验1: 基本加解密（同一明文 + 同一密钥）════════
明文: "AES mode compare!" (19 bytes)

[CBC] 底层 aes API，一次调用完成：
  密文 (32 B): af7982f678f498be053f0ec06bc547ca6af8c104d68a13ff09242d851932e7dd
  解密: "0123456789abcdef0123456789abcdef"

[GCM] 底层 gcm API，加密时同时产出 Auth Tag：
  密文 (19 B): e662bb508229b51eb6fd1516a799bda526ea20
  Tag  (16 B): e98829bc727cb4ad1807c0b499863853
  解密: "AES mode compare!"

[CTR] 通用 cipher API，update + finish 两步（流式）：
  密文 (19 B): 4a9a2ed1347872567ef9e478b801b7677b6e69
  解密: "AES mode compare!"

→ 三种模式都能正确加解密，但 API 形态各不相同：
  CBC: 一次调用，要求 16 字节对齐
  GCM: 一次调用，额外产出 16 字节 Tag
  CTR: update/finish 两步，流式接口

════════ 实验2: 密文长度对比（明文 = 19 字节）════════

  模式    明文长度   密文长度   额外开销        说明
  ─────────────────────────────────────────────────────
  CBC      19 B       32 B       +13 B         padding 到 16 字节对齐
  GCM      19 B       19 B       +16 B Tag       密文等长，Tag 单独传输
  CTR      19 B       19 B       +0 B            密文等长，无额外开销

→ CBC 的 padding 使密文膨胀 68%，GCM/CTR 无膨胀
→ TLS 选 GCM：等长 + 自带认证，带宽和安全性兼得

════════ 实验3: 篡改检测（密文首字节 XOR 0x01）════════

[CBC] 篡改后解密：
  解密结果: `.I.Q.......B...1123456789abcdef
  → 解密没有报错，但输出是乱码（静默损坏，无法检测）

[GCM] 篡改后解密：
  → 认证失败 (ret = -0x0012)，篡改被成功检测！
  → GCM 的 Auth Tag 保证了数据完整性

[CTR] 篡改后解密：
  解密结果: @ES mode compare!..
  → 解密没有报错，但输出是乱码（静默损坏，无法检测）

→ 只有 GCM 能检测篡改，CBC/CTR 的损坏是静默的
→ 这就是 TLS 必须用 AEAD 模式（GCM/CCM）的根本原因

════════ 实验4: 通用 Cipher API（运行时切换算法）════════

[通用 API → CBC]
  算法: AES-256-CBC, 密钥: 256 bits, IV: 16 bytes
  密文长度: 16 bytes (含 padding)

[通用 API → GCM (AEAD)]
  算法: AES-256-GCM, 密钥: 256 bits, IV: 12 bytes
  密文+Tag 长度: 39 bytes (密文 23 + Tag 16)
  解密: "Generic cipher API demo"

[通用 API → GCM (流式接口)]
  调用序列: set_iv → reset → update_ad → update → finish → write_tag/check_tag
  密文: 23 bytes, Tag: 16 bytes
  密文 (23 B): e04286159d2fb25bf5f70a13b28aef8157a300aa702155
  Tag  (16 B): 45fae076dc00b73f459cb30b210b8adf
  解密: "Generic cipher API demo" (Tag 验证通过)

→ 通用 API 的优势：切换算法只改 type 参数，代码结构不变
→ CBC 用 update/finish；GCM 可用 auth_ext 一次性接口或流式接口
→ GCM 流式: set_iv → reset → update_ad → update → finish → write/check_tag

══════════════════════════════════════════════════════
  模式    padding   密文长度   完整性   TLS 适用性
  ─────────────────────────────────────────────────────
  CBC     需要      膨胀       无       不推荐
  GCM     不需要    等长+Tag   有(AEAD)  首选 ✓
  CTR     不需要    等长       无       可用但需额外 MAC
